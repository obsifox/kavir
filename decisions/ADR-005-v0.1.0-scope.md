# ADR-005: v0.1.0 scope and milestone plan (v2 — walking skeleton)

Status: proposed (v1 REJECTED by the user 2026-10-26; re-proposed per the
user's instruction: walking-skeleton milestone order plus an explicit cost
estimate for the ADR-002 v2 custom-backend path)
Date: 2026-10-26 (v2)
Question: What exactly does the first published version contain — and in
what ORDER is it built?

User constraint (binding, 2026-10-26): the milestone order must be a
WALKING SKELETON — first make one trivial program (`return 42`) work END
TO END from lexer to an executable ELF, then add capabilities one at a
time. The scope must be re-derived from a cost estimate of the codegen +
ELF writer + runtime that ADR-002 v2 puts on us.

Cost estimate (honest, assumption-tagged; unit = compiler source LOC in
C17. Reference class: QBE is ~12k LOC for a 3-target OPTIMIZING backend
(C-413); naive correctness-first x86-64 codegen in small compilers is
1-2k LOC class work; our numbers below are estimates, falsified by M1):

  x86-64 codegen (IR lowering, instruction selection, two-address fixes,
    naive register allocation with spills, small peephole):  3-5k LOC
  ELF writer (static ET_EXEC, program headers, no relocations,
    no dynamic section):                                     0.5-1k LOC
  kavirrt (_start, syscall shims, bump allocator, u64-to-decimal,
    exit):                                                   0.3-0.6k LOC
  Frontend for v0.1.0 (lexer, parser, checker per ADR-003/004 subsets,
    IR construction):                                        4-6k LOC
  Tooling + tests (driver, kavir test, conformance suite, fuzz targets,
    formatter):                                              1-2k LOC
  TOTAL:                                                     ~9-15k LOC

Effort concentration: backend+ELF+runtime ~= 40%, frontend ~= 40%,
tooling/tests ~= 20%. The backend half is the NEW risk versus any
cc-based plan; it is de-risked FIRST by M1 (below), and ADR-002's
schedule gate (falsification gate 2) is defined on exactly this estimate.

Milestones (walking skeleton — each milestone is a runnable artifact with
its conformance tests green before the next starts; schedule pressure is
released ONLY through the ADR-003/004 cut lists, never by reordering):

  M1 WALKING SKELETON (non-negotiable, first):
     `fn main() -> i32 { return 42; }` compiles lexer -> parser ->
     checker -> IR -> x86-64 encoder -> static ELF; the binary exits 42.
     Proves the whole pipeline: _start ABI, ELF loadable by the kernel,
     syscall exit. No libc, no cc, no external tool anywhere in the path.
  M2 Output + arithmetic: string literals, u64->decimal print via
     write(2), integer arithmetic (+ - * / %), if/else. Test: prints
     "42\n" to stdout.
  M3 Flow + calls: while/loop/break/continue, let/let mut, comparisons,
     user function calls with arguments (SysV integer registers),
     recursion (fibonacci conformance test).
  M4 Aggregates: structs by value (<=16-byte integer-register classes
     first, SysV C-501), enums as tagged sums, match with
     exhaustiveness, Option[T] builtin.
  M5 Memory: brk-based bump arena, slices/pointers as data types, moves
     + lexical borrows per the ADR-003 subset, diagnostics for
     move/XOR-rule violations.
  M6 Tooling + generics core: monomorphizing generic structs/enums
     (builtins + user surface per the ADR-004 subset), unsafe block
     surface (per ADR-003 subset), kavir test, formatter, file:line:col
     error spans (C-313), reproducible-output flag (C-708 — our
     toolchain-independence makes byte-reproducible builds cheap).
  M7 Release engineering: fresh-install test on a clean machine, English
     + Persian docs and tour, honest README "Not yet" list,
     release_check.py full pass, tag v0.1.0.

Re-proposed v0.1.0 scope (= the M6 state minus whatever the ADR-003/004
cut lists were forced to remove under schedule pressure):
- IN: M1..M6 features; single tier-1 target x86_64-linux; static ELF, no
  libc, no cc anywhere in the compiled-program path (ADR-002 v2);
  single-crate multi-file modules with explicit imports, no registry, no
  network fetch; conformance suite + compiler fuzz targets (the compiler
  itself still builds with gcc — bootstrap boundary per ADR-002);
  English + Persian docs.
- OUT ("Not yet" list, published honestly): lifetime inference/NLL,
  borrow returns, struct-field borrows, closures, traits/bounds beyond
  the monomorphizing core, custom destructors (Drop), threads and any
  concurrency, async, macros, package registry/network fetching, second
  target (arm64), PIE/dynamic linking, DWARF beyond line tables,
  C-library FFI, any performance claims (measured numbers only, if any).

Options considered:
  A. Broad ambitious surface before any release. REJECTED (unchanged):
     the never-ships pattern (Perl 6 / Crystal pre-1.0 limbo, C-722..C-725;
     package infrastructure is its own project, C-701..C-706; stdlib
     freezes carry permanent compat cost, C-715).
  B. Narrow honest vertical slice — direction RETAINED, but v1's fixed
     bundle order was REJECTED by the user: features must ride on a
     working end-to-end skeleton (this v2).
  C. No public release until industrial parity. REJECTED (unchanged):
     not honest, not credible (feasibility-report section 2).

Trade-offs: the walking skeleton spends the riskiest work FIRST (ELF/ABI
de-risked by M1), converts schedule pressure into scope cuts instead of
slipped releases, and makes every intermediate commit a demoable artifact.
Cost: M1's artifact is useless as a language (an exit code only) and no
external benchmark or user can do anything with it — accepted, it is the
price of de-risking the custom backend.

Decision (RE-PROPOSAL to the user — awaiting approval): Option B on the
milestone ladder M1..M7 above, with the ADR-003/004 cut lists as the only
pressure valve; on approval, M1 starts Phase 3 immediately.

Reversibility (cheap / costly / one-way): the scope cut itself is cheap
(additive later); the milestone order is the user's binding constraint;
publishing claims is the one-way part — hence release_check.py and the
README rules.

What result would show this was wrong (experiment or metric): (1) M1 not
achievable within the codegen+ELF+runtime LOC share estimated above —
then ADR-002's schedule gate fires and the binutils as/ld fallback is
re-decided explicitly with the user; (2) release checklist passes but
zero external users can run the tour example from README on a fresh
machine — cut again before publishing.
