# ADR-005: v0.1.0 scope and milestone plan (v3 — walking skeleton, calibrated)

Status: accepted (user approved v2 on 2026-10-26 with amendments a-d,
recorded here as v3; M1 is authorized to START IMMEDIATELY without
re-approval — stop only if a NEW irreversible decision becomes necessary)
Date: 2026-10-26 (v3)
Question: What exactly does the first published version contain — and in
what ORDER is it built?

User goal (unchanged): v0.1.0 ships a narrow honest slice; milestone order
is a walking skeleton (first `return 42` end-to-end, then features).
v0.1.0 remains x86_64-linux only; the platform path is ADR-006 and does
not change this scope.

Cost estimate (reference-class estimates; falsified by M1 and RE-CALIBRATED
at M3 per amendment (a). Unit = compiler source LOC in C17. The IR
interpreter and sanitizer-fuzz harness from amendment (b) are INCLUDED
below):

  x86-64 codegen (lowering, instruction selection, two-address fixes,
    naive register allocation with spills, small peephole):   3-5k LOC
  ELF writer (static ET_EXEC, program headers, no relocations,
    no dynamic section):                                      0.5-1k LOC
  kavirrt (_start, syscall shims, bump allocator, u64-to-decimal,
    exit):                                                    0.3-0.6k LOC
  Frontend for v0.1.0 (lexer, parser, checker per ADR-003/004 subsets,
    IR construction):                                         4-6k LOC
  IR interpreter (reference semantics executor, amendment (b)):
                                                              1-1.5k LOC
  Tooling + tests (driver, kavir test, conformance suite, fuzz targets
    incl. sanitizer harness, formatter):                      2-3k LOC
  TOTAL:                                                      ~10-16k LOC

Amendments accepted from the user (2026-10-26, binding):

(a) CALIBRATION AT M3 (was: end-of-estimate falsification only). When M3
    goes green, the actual LOC / sessions / wall-time of backend + ELF +
    runtime are compared against this table and the remaining scope is
    formally reviewed there. The ADR-002 schedule gate (as/ld fallback
    re-decision) is also evaluated at the same point. M3 is the single
    scope-review checkpoint for v0.1.0.

(b) IR INTERPRETER AS CORRECTNESS REFERENCE, from M1/M2. `kavir interp`
    executes the same IR the backend consumes (the interpreter is the
    executable specification of Kavir semantics). EVERY codegen
    conformance test MUST compare the ELF behaviour (exit code; stdout
    from M2 on) against the interpreter's behaviour on the same program;
    a mismatch is a conformance failure and blocks the milestone. In
    addition, the lexer/parser/checker fuzz targets run under ASan+UBSan
    builds of the compiler (the compiler itself is built with gcc —
    bootstrap boundary per ADR-002 v2). Cost: included in the table
    above (interpreter 1-1.5k; harness ~0.2k inside tooling).

(c) M5-CUT CONTINGENCY — decided NOW, in advance. If the M3 calibration
    shows M5 (memory: arena, slices/pointers, moves + lexical borrows,
    diagnostics) does not fit, the release falls back to "0.1.0-m5cut":
    - Trigger (objective): projected remaining effort for M5+M6+M7,
      measured at M3 calibration, exceeds 2x the actual effort spent on
      M1..M3.
    - Minimum publishable scope in that case: M1..M4 features (integers,
      arithmetic, control flow, functions/recursion, structs/enums/
      match/Option — all by value), string literals + print (write
      syscall), kavir build/run/test/check, conformance suite +
      interpreter cross-check, reproducible-output flag, docs. NO heap
      or arena, NO slices/pointers as user types, NO references/borrows
      at the surface (ADR-003 borrow rules become vacuous for user code
      — builtins only), NO unsafe surface.
    - README claims FORBIDDEN in 0.1.0-m5cut: any memory-safety claim
      ("memory-safe", "prevents use-after-free / double-free / data
      races"), "safe language", any performance claim, any
      production-readiness claim. REQUIRED wording: "experimental;
      x86_64 Linux only; no heap model yet; no memory-safety guarantee
      is claimed for 0.1.0-m5cut". The soundness contract (ADR-004)
      still holds for the by-value surface, but it may not be advertised
      as memory safety.
(d) README explicitly states only x86_64 Linux is supported — DONE
    (2026-10-26, per ADR-006 companion work; Windows/macOS interim
    options documented there).

Milestones (walking skeleton — each milestone is a runnable artifact with
its conformance tests green before the next starts; schedule pressure is
released ONLY through the ADR-003/004 cut lists and amendment (c), never
by reordering):

  M1 WALKING SKELETON (non-negotiable, first):
     `fn main() -> i32 { return 42; }` compiles lexer -> parser ->
     checker -> IR -> x86-64 encoder -> static ELF; the binary exits 42.
     Includes from day one: the IR interpreter cross-check (amendment b),
     sanitizer fuzz over the frontend (amendment b), file:line:col
     diagnostics (C-313). Proves the whole pipeline: _start ABI, ELF
     loadable by the kernel, syscall exit. No libc, no cc, no external
     tool anywhere in the compiled-program path.
  M2 Output + arithmetic: string literals, u64->decimal print via
     write(2), integer arithmetic (+ - * / %), if/else; interpreter and
     ELF must agree on stdout as well.
  M3 Flow + calls: while/loop/break/continue, let/let mut, comparisons,
     user function calls with arguments (SysV integer registers),
     recursion (fibonacci conformance test). CALIBRATION CHECKPOINT
     (amendments a + c) at the end of M3.
  M4 Aggregates: structs by value (<=16-byte integer-register classes
     first, SysV C-501), enums as tagged sums, match with
     exhaustiveness, Option[T] builtin.
  M5 Memory: brk-based bump arena, slices/pointers as data types, moves
     + lexical borrows per the ADR-003 subset, diagnostics for
     move/XOR-rule violations. (Subject to amendment (c) trigger.)
  M6 Tooling + generics core: monomorphizing generic structs/enums
     (builtins + user surface per the ADR-004 subset), unsafe block
     surface (per ADR-003 subset), kavir test, formatter, reproducible-
     output flag (C-708).
  M7 Release engineering: fresh-install test on a clean machine, English
     + Persian docs and tour, honest README "Not yet" list,
     release_check.py full pass, tag v0.1.0.

Re-proposed v0.1.0 scope (= the M6 state minus whatever the ADR-003/004
cut lists and amendment (c) were forced to remove):
- IN: M1..M6 features; single tier-1 target x86_64-linux; static ELF, no
  libc, no cc anywhere in the compiled-program path (ADR-002 v2);
  single-crate multi-file modules with explicit imports, no registry, no
  network fetch; conformance suite + compiler fuzz targets under
  sanitizers; English + Persian docs.
- OUT ("Not yet" list, published honestly): lifetime inference/NLL,
  borrow returns, struct-field borrows, closures, traits/bounds beyond
  the monomorphizing core, custom destructors (Drop), threads and any
  concurrency, async, macros, package registry/network fetching, second
  target (arm64), PIE/dynamic linking, DWARF beyond line tables,
  C-library FFI, any performance claims (measured numbers only, if any).

Options considered:
  A. Broad ambitious surface before any release. REJECTED: the
     never-ships pattern (Perl 6 / Crystal pre-1.0 limbo, C-722..C-725;
     package infrastructure is its own project, C-701..C-706; stdlib
     freezes carry permanent compat cost, C-715).
  B. Narrow honest vertical slice on a walking-skeleton ladder (this v3).
  C. No public release until industrial parity. REJECTED: not honest, not
     credible (feasibility-report section 2).

Trade-offs: the walking skeleton spends the riskiest work FIRST (ELF/ABI
de-risked by M1), converts schedule pressure into scope cuts instead of
slipped releases, and makes every intermediate commit a demoable artifact.
The interpreter (amendment b) adds work now but buys an executable
specification and a second IR consumer — it is the cheapest possible
insurance for the IR-purity gate of ADR-002. Cost: M1's artifact is
useless as a language (an exit code only) — accepted, it is the price of
de-risking the custom backend.

Decision (ACCEPTED by the user, 2026-10-26, with amendments a-d):
Option B on the milestone ladder M1..M7, ADR-003/004 cut lists plus
amendment (c) as the only pressure valves; M1 starts immediately on
acceptance, without re-approval.

Reversibility (cheap / costly / one-way): the scope cut itself is cheap
(additive later); the milestone order is the user's binding constraint;
publishing claims is the one-way part — hence release_check.py and the
README rules.

What result would show this was wrong (falsification gates):
1. M1 not achievable within the codegen+ELF+runtime LOC share estimated
   above — ADR-002's schedule gate fires and the binutils as/ld fallback
   is re-decided explicitly with the user.
2. M3 calibration (amendment a) shows the estimate materially wrong —
   scope is re-derived there, with the m5cut fallback of amendment (c).
3. Release checklist passes but zero external users can run the tour
   example from README on a fresh machine — cut again before publishing.
4. Any interpreter/ELF behaviour mismatch on a conformance test is a
   conformance failure by definition (amendment b) — the milestone does
   not pass while mismatches exist.
